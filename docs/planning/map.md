# Auto clicker: project map

## Purpose

An auto clicker with macro record and playback for Wayland desktops on CachyOS, made for playing games: KDE Plasma first, and niri and Hyprland from W01 (#75). It should match what common auto clickers offer, live in the system tray, and cost next to nothing while idle.

## Users and use cases

- **Repeating a routine:** record a sequence of mouse movements, clicks and key presses with their timing, then replay it once, N times or until stopped.
- **Minecraft-style games:** fast left or right clicking, holding a button or key down (attack, walk forward), toggled by a hotkey while the game has focus. These games often lock the pointer, so recorded movement must replay as relative motion there.

## Platform facts (checked 2026-11-09)

- Plasma 6.8 (October 2026) removed the X11 session; the target laptop runs Plasma 6.8.2, KWin 6.8.2, xdg-desktop-portal 1.22.1, xdg-desktop-portal-kde 6.8.2 and libei 1.6.0. **Wayland is the primary target from day one.** X11 games keep running under XWayland and must work.
- Wayland lets no client inject input into another or read the global pointer position. Two ways in:
  - **Kernel backend:** read real devices with evdev and inject through a uinput virtual device. Works on any compositor with no prompt. Injecting needs write access to `/dev/uinput` (a uaccess udev rule is enough); reading devices for hotkeys and recording needs read access to `/dev/input/event*`, in practice the `input` group, which means the program can technically read every keystroke.
  - **Portal backend** (X02, [decision 0002](../decisions/0002-portal-backend.md), Plasma 6.8.2): libei through the RemoteDesktop portal for output and the GlobalShortcuts portal for hotkeys both work. The RemoteDesktop prompt shows once and its restore token survives restarts and reboots. The GlobalShortcuts dialog shows once, but the program must bind on every start and cannot change a binding itself (System Settings does, through `ConfigureShortcuts`). An activation names the shortcut and no device, so with portal hotkeys the program never presses a hotkey's key (P02, #20). KWin releases everything a libei device held when the program dies or the session closes. GlobalShortcuts refuses a program without an app id, and RemoteDesktop scopes its grant by it: the package installs `io.github.tobylo.AutoClicker.desktop` and the user service is `auto-clicker.service` (C05), so the daemon calls `Registry.Register` before its first portal session (P01, #19). InputCapture cannot record gameplay: capture starts when the pointer crosses a barrier at a screen edge, and while it lasts the focused window receives no input at all (measured: 0 events). No portal or KWin interface observes input while leaving it with the game, so recording stays on the kernel backend.
  - Detection works per capability (output, hotkeys, recording). The target laptop is the mixed case: `/dev/uinput` is writable through uaccess, but `/dev/input/event*` is not readable without the `input` group, so output has a kernel route, hotkeys only a portal route, and recording none.
- **niri and Hyprland** (W01, [decision 0004](../decisions/0004-pointer-mapping-on-niri-and-hyprland.md), 2026-11-12). The kernel route runs on niri 26.04 unchanged (C02, C04, R02). Both compositors report every output's logical place and size through xdg-output, which any Wayland client reads. niri maps the virtual mouse's absolute axes over the bounding box of its outputs, as KWin does, but over ceil(physical/scale) while it reports round(physical/scale): up to 1 logical px off near the far edges at such fractional scales (measured). niri 26.04 gives no client the pointer's position; ext-image-copy-capture cursor sessions on its main branch will. Hyprland 0.57 maps like KWin and gives the pointer through `cursorpos` on its socket and through cursor sessions (read from source; W01c measures). Neither runs a tray of its own: users run a bar with a StatusNotifierItem tray.
- No existing Linux tool combines record and playback with a Plasma tray icon. theclicker-gui (Rust, uinput, SNI tray) and clickr (Rust, uinput) are references for the clicker part.

## Decisions

| # | Decision | Why |
| --- | --- | --- |
| D1 | Rust, one small daemon; tray via `ksni` (StatusNotifierItem) | Low idle cost; SNI is Plasma's native tray protocol |
| D2 | Both input backends in v1, behind one backend trait: kernel first (M1–M2), portal in M4, chosen per capability (`[input] output` and `hotkeys`, each `"auto" \| "kernel" \| "portal"`, default `"auto"`; P01, P02, P04). `auto` is decided once at start: the kernel where the program has access (`/dev/uinput` opens; a keyboard with the hotkey keys is readable), the portal otherwise, unless the portal is absent or too old. An explicit route is used as written. A job without a working route keeps the daemon in the tray with the reason and the fix, and the next start tries again; the screen layout's and positions' sources are picked the same way, by what answers and belongs to the session's display: KWin's scripts (followed through `org.kde.KWin`'s owner), xdg-output or Hyprland's position source (picked once at start), or none (W01, [brief](features/w01-other-desktops.md)); a route change applies from the next start (P04). Portal hotkeys use one GlobalShortcuts session for the daemon's life, bound again when the portal service returns; System Settings owns the triggers from the first bind on (P02). The portal session opens for each run and closes after it, so the desktop shows remote control only while clicking (P01). On the portal backend, recording is unavailable: X02 found no mechanism that leaves input with the game ([0002](../decisions/0002-portal-backend.md)). Wherever recording cannot start (the desktop's shortcuts, no `input` group, or a failed watch for keyboards), the tray's Record item is off and names the reason, the tooltip gives the fix, and the record shortcut stays registered and answers with a notice (P03) | Kernel works today with no prompts; the portal avoids the `input` group; InputCapture takes input away from the focused app by design |
| D3 | Recording captures clicks, keys, timing and mouse movement, including absolute cursor positions. X01 settled how ([decision 0001](../decisions/0001-cursor-position.md)): while recording, the daemon loads a KWin script (the position script) that reports `workspace.cursorPos` (whole logical px) over D-Bus, and unloads it at stop. Playback moves the absolute axes to `round(x * 65536 / W)`, with W and H the size of KWin's layout, landing within 0.65 physical px per axis of where the real pointer was on one and two monitors at scales 1 to 1.5 (the bound grows with the scale; see the decision's limitations). R03 (#16) is refined into two slices ([feature brief](features/r03-absolute-positions.md)): a recording stores positions and the layout it was made on (format version 2); playback uses the positions when the outputs they lie on are unchanged and relative motion otherwise, saying so; a second script, the layout script, reports the layout alone and stays loaded while the daemon runs. R03b wired it: crate `backend-kwin` loads both scripts through `/Scripting` and receives their calls on the daemon's own bus name, so recordings made on Plasma hold positions and write version 2 whenever KWin's scripts report; without them a recording keeps movement only, in version 1. W01 (#75, [feature brief](features/w01-other-desktops.md)) brings the layout to every Wayland desktop through xdg-output, moved to start at (0, 0) (Plasma too: it matched KWin's layout in every case measured), and positions to Hyprland; niri keeps movement only until a release offers cursor sessions (W02) | Under Wayland only the compositor knows the cursor position; KWin scripts read it with no consent, about 1 ms behind at most, and cost nothing while idle |
| D4 | Movement is recorded both as relative motion and, when available, absolute positions; playback uses relative motion while a game has locked the pointer | Minecraft-style games lock the pointer |
| D5 | Settings window in Slint, opened from the tray and loaded only while open; everyday use is tray plus hotkeys | Settings without editing a file, and without raising idle cost |
| D6 | Hotkeys default to Ctrl+Shift+F6 (clicking on/off), Ctrl+Shift+F7 (record on/off), Ctrl+Shift+F8 (play/stop), rebindable: in the config on the kernel route, in System Settings on the portal route | Free in stock Plasma, where Ctrl+F7, Ctrl+F9, Ctrl+F10 and Super+F1 to F7 are taken (X02, P02); Minecraft binds nothing to F6, F7 or F8 |
| D7 | Recordings and config are TOML/JSON files under XDG paths (`~/.config/auto-clicker/`, `~/.local/share/auto-clicker/`) written atomically. Recordings (R01) are JSON, one file each in `recordings/`: version 1, or version 2 when the recording holds positions (R03: the layout it was made on and `"at"` events; a recording without positions is still written as version 1, and both versions are read), held in memory while recording and written once at the stop, renamed into place without replacing (`RENAME_NOREPLACE`). One reader of `/dev/input` serves hotkeys and recording; it opens mice only while recording | Simple, inspectable, survives crashes; idle stays free |
| D8 | Install through a PKGBUILD with a udev rule and a systemd user service | CachyOS is Arch-based |
| D10 | Code reaches the machine only from this repository: v1 installs by the owner building a reviewed commit and has no network access; a later updater may fetch only signed releases of `tobylo/auto-clicker`, verified against the owner's pinned key. Dependencies from crates.io only, locked, and checked for advisories in CI | The program has access to input devices; nobody but the owner may be able to push code to a machine that runs it |
| D9 | Review services: Codex and CodeRabbit GitHub bots, CodeScene Code Health. No Entire | Owner's choice |
| D11 | The daemon runs on tokio's single-thread (`current_thread`) runtime. Timers sleep until absolute deadlines (`sleep_until`), and every wait selects on its deadline, the stop signal and shutdown. Tests use tokio's paused clock | One thread is enough for a tray program and costs nothing while idle; absolute deadlines keep delays from adding up; the paused clock checks schedules and "stops at once" exactly, without real waiting (#10) |

## Clicker options and measurements

- Clicker options: interval in ms or clicks per second, random jitter (up to ±50%), left/right/middle/back/forward, single or double click, hold a button or a key down, key-repeat mode, at cursor or at a fixed point, repeat count or until stopped.
- **Fastest stable interval: 10 ms** (C02, 2026-11-09, niri 26.04 on the dev box, uinput, release build; `scripts/measure-clicker.py`). A test window received 1000 of 1000 clicks at every interval tried, down to 2 ms. The limit is timing: tokio's timer has 1 ms resolution, so each period is off by up to about 0.9 ms, which stays under 10% of the interval from 10 ms up (10 ms: 9.3%, 12 ms: 7.7%, 15 ms: 6.0%) and exceeds it below (8 ms: 11.2%, 5 ms: 18.5%; measured on a local build with `INTERVAL_FLOOR` set to 1 ms, since the config rejects intervals under the floor). The mean period is exact. On the busy dev box, some runs at any interval also had one late period of 2 to 10 ms from scheduling; their 99th percentile stayed under 1 ms. The interval floor is therefore 10 ms (20 ms for a double click, which fits two clicks in each interval).
- **Idle cost of the engine** (same setup, 60 s each): clicking once a second used 0 CPU ticks (under 10 ms of CPU) and 209 context switches, about two wakeups per click (press, then release after the hold) plus a few more; holding a button used 0 ticks and 0 context switches.
- **Playback** (R02, #15). A recording plays through the same run machinery as clicking (one wait that selects on its deadline, stop and shutdown; everything released at the end). Each event is due at `start + (round * duration + offset) / speed`, computed from the run's start every time, so nothing adds up; events already due fire in order, and a late one does not move the rest. Speed is 0.25 to 4, repeats are a count or until stopped, and a recording under 100 ms plays once only. Measured 2026-11-10 on niri 26.04 on the dev box, uinput, debug build (`crates/backend-kernel/tests/playback.rs`): replaying a 20-event routine twice at speed 1.5 and recording the replay from the virtual devices, every event was within 1.3 ms of its place, over two runs. Replayed relative motion passes through the compositor's pointer acceleration: 400 units moved the pointer 397 px recorded slowly and played at quarter speed, and 790 px recorded or played fast (niri's default adaptive profile; Plasma 6.8.2 on the laptop gave the same figures, 397 to 795 px). Pointer-locked games get the raw deltas. A key the user holds while playback presses and releases the same key stays down for the window until the user lets go on Plasma 6.8.2; on niri the window sees it come up at playback's release.
- **Settings window** (U01, #17). A program of its own (`auto-clicker-settings`, Slint 1.18 with only the Wayland winit backend and the femtovg renderer, under Slint's royalty-free licence), started by the daemon with a socket pair as its standard input, one at a time; the daemon never loads Slint. The window sends requests as JSON lines; the controller checks a save with the config file's own rules, writes the canonical file atomically, and sends the window a fresh view after every change. Saves wait until nothing runs; saved hotkeys apply at once by starting the keyboard reader again, the rest from the next start. Captures run in the daemon's keyboard reader and end on every way out; with `hotkeys = "portal"`, the window opens Plasma's shortcut settings through `ConfigureShortcuts`. Measured 2026-11-11 on Plasma 6.8.2 on the laptop, release builds of the daemon and the window made separately (as the package builds them): the daemon idles at 7.0 to 7.2 MiB with 2 threads (main's daemon: 6.8 MiB and the same 2 threads on that machine); the first window adds 0.1 MiB that stay (tokio's child-process handling), and five open and close cycles after it left the daemon at the same figure; the window itself uses about 122 MiB while open.
- **Recordings manager** (U02, #18). The window's Playback tab lists the newest 200 recordings (the tray keeps its ten), each by the name in its file's header, read from the file's first 4 KiB in the program's own header form, beside the time in its file name. Renaming rewrites the whole file atomically under the same file name; deleting is permanent, after a Yes/No in the window; Play starts the tray's countdown. The recording the playback hotkey plays is state, not a setting: one file name in `$XDG_STATE_HOME/auto-clicker/current-recording`, written atomically only when it changes (a choice in the window, a play from the tray or the hotkey, a new recording), and a missing or invalid file means the newest. Every action waits until nothing runs, like a save, so no file work ever delays a stop; a window opened mid-run gets its longer list once the program is idle.
- **Picking the fixed point** (U03, #28). "Pick on the screen…" opens a full-screen overlay on every screen, made full-screen on its screen through Slint's winit backend (Wayland only); the next left click picks, and Esc, closing an overlay or 30 s cancel. The window sends the point in logical pixels to a fraction of a pixel (its screen's corner, from KWin's layout in the window's view, plus the click), with the counts of runs begun and screen changes its view showed when the pick began; the controller maps it with decision 0001's formula only while idle, only if neither count moved since and only while that screen is still in KWin's layout, so a run's own click is never taken for a pick. The window fills in the point; Save keeps it with the screens it was picked on (`screens` in the config), and a click mode at a picked point starts only on the same screens and stops when they change or become unknown. A typed point keeps no screens.
- **The user's language** (U04, #60). Core says what happened as values (`message::Notice`, `Problem`, the window's `Failure`, `Unavailability` and the settings' `Reason`), each with its English as `Display`; the tray renders them in Swedish from its own table and the settings window through its `@tr` catalogue, both chosen by #17's locale rule. Text from another program (an I/O error, a portal's reason, a parser's message) is quoted as it is, cut to `MAX_TEXT` on its way to the window, which refuses longer. Why a config or recording file does not parse stays the parser's English.
- **Idle cost of the daemon** (C04, 2026-11-10, niri 26.04 on the dev box, release build, `scripts/measure-daemon.py`, 60 s with the tray icon shown, hotkeys read and logind followed): 0 CPU ticks, 0 context switches, 1 thread, 5.8 MiB resident. The release binary is 3.7 MB.

## Open questions

- Which way Hyprland's positions come: `cursorpos` asked on each mouse move (the default) or ext-image-copy-capture cursor sessions. W01c measures both against R03's 2 ms and 5 ms windows and asks the owner if the default misses, costs a game frame time or covers a locked pointer's moves.
- Does the next machine the program is installed on also run Plasma 6.8? Assumed yes (CachyOS is rolling).
- Do the target games accept uinput clicks? Minecraft Java does, both as a native Wayland window and under XWayland, on the target laptop (Plasma 6.8.2). As a native Wayland window, 10 of 10 slow right clicks and 1000 of 1000 at the 10 ms floor registered (Statistics, snowballs "Times Used"; C02, 2026-11-09). Under XWayland, 1000 of 1000 at the 10 ms floor registered, and Ctrl+Shift+F6 holds started and stopped mining in fullscreen while the game still got Shift (#32, 2026-11-12; [0003](../decisions/0003-minecraft-under-xwayland.md)). Minecraft 26.3 opens its window through SDL, so `SDL_VIDEO_DRIVER=x11` in the launcher's environment puts the game on XWayland; `latest.log` then says `Created window using SDL video driver: x11`. Start the launcher through the package's `minecraft-launcher.sh`, which works around a known launcher crash (MCL-25003). Started directly, the launcher crashes with or without Wayland, which is what stopped the first try in #32.
