# W01: Run well on niri and Hyprland

- Issue: [#75](https://github.com/tobylo/auto-clicker/issues/75), a Feature after the 1.0 milestones (M0 to M4). Slices: W01a (#77), W01b (#80), W01c (#78), W01d (#81), W01e (#82). Follow-up outside this feature: W02 (#79), positions on niri.
- Maturity: refined 2026-11-12, ready to slice. Rests on [decision 0001](../../decisions/0001-cursor-position.md), [decision 0004](../../decisions/0004-pointer-mapping-on-niri-and-hyprland.md), the [R03 brief](r03-absolute-positions.md) and map D2, D3, D4, D7, D11.
- Diagram: [start, detection, the layout and position sources, and where they are used](https://prlens.dev/c/9ovByKl0Mo9_uUmEkE4eaQ).

## Problem and outcome

Clicking, hotkeys, recording and playback of relative movement already work on niri and Hyprland on the kernel route (C02, C04 and R02 were measured on niri 26.04). Two things still come only from KWin: the screen layout, which "Pick on the screen…", the fixed point's screens check and playback's screens check need; and the pointer's position in recordings. With W01 the layout comes from xdg-output on every Wayland desktop, Hyprland recordings hold positions, and wherever a part cannot work the tray says why.

## Scope

In scope: a layout source on xdg-output for every desktop, Plasma included (it matches KWin's layout, decision 0004); picking the sources at start; positions on Hyprland; the tray's and tooltip's wording for a missing source; the README for niri and Hyprland users.

Out of scope: GNOME; the ScreenCast portal as a position source; the portal route on niri and Hyprland (`auto` already falls back to the kernel route); a tray of the program's own (niri and Hyprland users run a bar with a StatusNotifierItem tray); positions on niri (W02, waiting for a niri release with ext-image-copy-capture cursor sessions, [0004](../../decisions/0004-pointer-mapping-on-niri-and-hyprland.md)); working around niri's rounding (decision 8); a virtual device the user binds to one output in Hyprland's config (the README says positions and picking assume it is not).

## Invariants

These hold everywhere below and are stated once. R03's I1 to I5 still hold.

- **W1, sources are picked by what answers, and belong to the display.** KWin is followed through `org.kde.KWin`'s owner for the daemon's life, as today, whatever was found at start. The xdg-output source and Hyprland's position source are picked once at start, after the single-instance name is claimed, by capability: xdg-output when the Wayland connection offers `zxdg_output_manager_v1`, Hyprland's positions by the capability W01c's route needs. Never by a desktop's name. A compositor source counts only when it is the compositor of the daemon's Wayland display (KWin's owner, Hyprland's socket): another session's KWin on the same user bus, a nested compositor or a stale `HYPRLAND_INSTANCE_SIGNATURE` is ignored. A source that is missing leaves its part unknown, with the reason kept for the tray; a restart tries again. Since W01b the layout comes from xdg-output on Plasma too, and KWin gives positions only.
- **W2, nothing outside a backend crate talks to a compositor.** The controller sees the layout and positions only through `Platform::layout`, `Platform::pointer` (since W01e) and `Platform::watch_layout`.
- **W3, a layout is one coherent snapshot starting at (0, 0).** A layout is published only once every output's update of one change has arrived; until then the last whole layout stands. The protocols mark the end of an update per output, not of a change across outputs, so "every output's update" is what the compositor queued before it answered the client's round trip: niri, KWin and Hyprland queue a whole change first (decision 0004, from source); one that did not would show a change as two layouts, each firing. An update that moves no output (a new refresh rate, a repeated notice) publishes nothing. An unknown layout stops fixed-point clicking and a playback using positions, so a passing update must not make it unknown. niri and Hyprland allow outputs at negative positions and map the absolute device over the bounding box wherever it lies, so the source moves the box to (0, 0) before `Layout::new`, and the pick overlay moves winit's monitor corners by the same offset.
- **W4, a position belongs to the layout it was taken on.** A position is moved by that layout's offset and checked against it, never against a later one. When the position and the layout arrive on different channels (a socket or D-Bus beside the Wayland connection) and the position carries no mark of its layout, a position stamped within a bound before a layout change is dropped, so one taken on the new screens is never written against the old. The bound is how late that compositor's layout notice can trail a position on the new screens, measured with margin (W01c for Hyprland); a source whose positions carry their layout (a cursor session on the Wayland connection, a script's report) uses that instead. On Plasma the position script reports the layout at load and on every change, and each position is judged by the last layout reported before it: measured, D-Bus ran 200 ms late under load, after xdg-output's notice, so no window would have bounded it (W01b, decision 0004).
- **W5, a lost compositor.** A Wayland connection that ends, or a protocol error on it, makes the layout unknown and never ends the daemon. On niri and Hyprland it stays unknown for the daemon's life: their session is ending. On Plasma, KWin restarts within the session (`kwin_wayland_wrapper`), so each owner of `org.kde.KWin` that runs the display has the source connect again to the same listener, with no deadline, the first one the daemon sees included (the connection made at start may be to a KWin gone since, or may have timed out); a newer one starts that over (W01b).
- **W6, every request to a compositor is bounded.** R03's I5 applies to every compositor, not only KWin: each request has its own deadline, at most one is in flight, its reply is read to a small fixed limit and parsed once into a validated type, and a failure or a late reply is no position, never a failed or blocked recording. Every request, deadline and session a recording starts ends with it. The one exception is the layout connection's round trip (`wl_display.sync`), and on Plasma the connection made again for each KWin of the display, which waits the same way and ends at a newer KWin or shutdown: it is part of the connection's wait for the compositor's events, which may last indefinitely (W7, and AGENTS.md's idle wait), and a compositor that never answers leaves the last whole layout standing; it runs no timer and never blocks a recording, a stop or shutdown.
- **W7, idle costs nothing; locked motion stays relative.** The Wayland connection wakes only on the compositor's events. Positions are read only while a recording runs: asked on motion, at its start, and once more after the last motion the per-millisecond cap or an ask in flight held back, as soon as the ask in flight is answered and 1 ms has passed since the last ask went out (a deadline bound to the recording, not a poll). While a game holds the pointer, no position may cover its relative moves (map D4): a route that cannot tell is not used, unless playback of the recordings it makes sends every relative move, covered or not, and the compositors they play on ignore absolute moves while a lock holds (Hyprland, decisions 15 and 17).

## Behaviour

**Layout (W01a).** On a desktop with xdg-output, the daemon binds every `wl_output` (up to `MAX_OUTPUTS`) and its xdg-output, and takes each output's logical position and size. The watcher signals every change, as KWin's does. Picking the fixed point, the fixed point's screens check and playback's screens check then work as on Plasma. On niri at a fractional scale where physical/scale is not whole, a point near the far edges lands up to 1 logical px off (decision 8).

**Plasma (W01b).** xdg-output's layout matched KWin's on the laptop in all seven layouts tried, at scales 1, 1.25 and 1.5, with fractional-width outputs left of and above the other (decision 0004, 2026-11-12). So W01b moves Plasma's layout to xdg-output and removes the layout script. The position script stays, and reports the layout at its load and on every change of the screens; each position is kept only while the layout reported before it has the recording's screens, which xdg-output gave at the recording's start (W4). A KWin restart reconnects (W5).

**Hyprland positions (W01c, W01d).** W01c measures, on Hyprland 0.57 as the session on the laptop (two monitors) and the dev box: the absolute device's mapping on one and two outputs, a negative position included; xdg-output against Hyprland's monitor sizes; and two position routes. Route A asks `cursorpos` over Hyprland's socket on each evdev motion event, at most once per millisecond. Route B uses ext-image-copy-capture cursor sessions. For each: the cost to Hyprland's frame time while a game runs (Route A opens a connection per ask), how late a position is against R03's 2 ms delivery delay and 5 ms cover window, how often it describes the pointer before the move behind it, whether it keeps a locked pointer's moves uncovered (W7), and how late xdg-output's notice of a layout change trails a position on the new screens (W4's bound). Route A is the default (decision 3). W01c brings the owner the choice with its numbers if Route A misses the windows, costs a game frame time or fails W7; the owner decides. W01d builds the route decided, feeding the recorder through `RecordingFeed` as KWin's watcher does, with the layout each position was taken on (W4).

Measured by W01c (decision 0004, 2026-11-13): Hyprland maps like KWin and xdg-output matches it in every layout tried. Route A answered inside R03's 5 ms window as KWin's script does, though more often over 2 ms (under Minecraft, 2.2 % of moves against KWin's 0.29 %; none over 5 ms), never with a stale position, and cost Hyprland no frame. Route B missed the 2 ms window for about half the moves or more. But Hyprland's locked pointer drifts, by a few px in most runs (an early return in `InputManager.cpp:259`), so `cursorpos` changes while a game holds the pointer and would cover 5 % (Minecraft) to 100 % (steady steps) of its moves; nothing tells a lock from outside. Hyprland ignores absolute moves while a lock holds. The owner chose Route A with every relative move sent at playback (decision 15). W4's bound is 10 ms for a position stamped when its answer is read (3.12 ms measured). W01d built it: crate `backend-hyprland`, picked at start when the socket belongs to the display, asked on motion while recording, its recordings written as version 3 ("Settled by W01d").

**Saying what is missing (W01e).** When a recording keeps movement only because no position source exists on this desktop, or no Wayland display was given, the tray's Record item and tooltip say why, in the user's language (U04), and picking says why its screens are unknown. W01d adds Hyprland's own reasons (its socket did not answer, or belongs to another display) with their wording. The README recommends the flat pointer acceleration profile where positions are missing; says how to start the user service on niri and on Hyprland (plain Hyprland never starts `graphical-session.target`, so uwsm or a line in its config; `WAYLAND_DISPLAY` and, on Hyprland, `HYPRLAND_INSTANCE_SIGNATURE` in the systemd user environment, cleared when the session ends); and brings its statements about picking and positions in step with W01 (niri's rounding, picking without KWin, positions on Hyprland).

## Decisions

Settled before refinement (the owner, 2026-11-12):
1. niri and Hyprland are the target desktops; GNOME is out of scope; the ScreenCast portal is out of scope unless the owner asks for a spike.
2. The kernel route already runs on niri; nothing in W01 changes clicking, hotkeys or relative recording.
3. Positions are per compositor: KWin's position script stays on Plasma. Where a compositor answers only when asked (Hyprland's `cursorpos`), the daemon asks on each evdev motion event with a cap, never on a timer. W7's last ask is a deadline set by motion while recording, not a poll.
4. Without positions, recordings keep relative movement and the tray says why; the README recommends the flat acceleration profile.
5. From R03: playback uses positions only on unchanged outputs, relative motion otherwise; a layout change stops a playback using positions.

Decided by the owner in refinement (2026-11-12):
6. **Five slices**, with a Hyprland measurement (W01c) before Hyprland positions are built, and the Plasma switch (W01b) apart from the new source.
7. **Wayland client:** `wayland-client` and `wayland-protocols`, both already in `Cargo.lock` through the settings window, pure Rust. A prototype measured 0 CPU ticks and 0 context switches over 60 s idle, +240 KiB resident and +202 KB of binary (decision 0004).
8. **niri's rounding:** accepted. niri maps the absolute device over ceil(physical/scale) while xdg-output reports round(physical/scale), so where they differ a point near the far edges lands up to 1 logical px off. Recorded in decision 0004 and the README; the owner gets the facts for an upstream report. No workaround: it would copy niri's rounding and break silently when niri changes it.
9. **Plasma:** moves to xdg-output in W01 if xdg-output agrees with KWin's layout in every case measured. It did (decision 0004), so W01b makes the move.
10. **Hyprland's route:** W01c measures both routes; decision 3's route stands unless the numbers show it costs a game frame time, misses R03's windows or fails W7, and then the owner chooses.
11. **Hyprland is installed** on the laptop and the dev box for W01c; the owner logs into a Hyprland session once on each.

Defaults (reviewed; go ahead without asking):
12. Invariants W1 to W7.
13. niri: no upstream request for a pointer command. Its maintainer has declined one (niri PR #1924) and points to ext-image-copy-capture cursor sessions, already on niri's main branch (0004). W02 takes it up once a release ships them.
14. Decision record 0004 holds every measurement, each marked measured or read from source; W01a and W01c add theirs.

Decided by the owner after W01c (2026-11-13):
15. **Hyprland's route:** Route A, `cursorpos` on each evdev motion event (decision 3). Since its positions cover a locked game's moves, playback on Hyprland sends every relative move, covered or not, followed by its position: a locked game ignores the position (Hyprland drops absolute motion during a lock, measured) and keeps all its moves; on the desktop the position corrects the pointer within 5 ms. This changes R03 decision 8's skip rule on Hyprland only; Plasma keeps it. (Reworded by decision 17: the rule follows the recording, not the desktop it plays on.)

Decided by the owner in W01d (2026-11-13):
16. **Floored positions:** a recording whose positions Hyprland reported is format version 3, version 2 with `"positions_from":"hyprland"`, and its positions replay from the middle of their pixel: at most 0.5 logical px off, 0.8 physical px at scale 1.6, against 1.6 physical px replayed as stored. Plasma's recordings stay version 2. Builds before W01d do not read version 3.
17. **Where the playback rule comes from:** a version 3 recording sends every relative move wherever it plays; a version 2 recording keeps R03 decision 8's skip rule wherever it plays, Hyprland included (KWin's positions never cover a game's moves, decision 0001). So a Hyprland recording played on Plasma keeps a game's moves: KWin 6.8.2 ignored 2,000 of 2,000 absolute moves while a window held the pointer, and passed every relative move before and after (decision 0004, W01d). No platform switch tells playback the rule.

2. The layout comes from xdg-output on niri and Hyprland, is published only whole, follows screen changes, starts at (0, 0) whatever the outputs' positions, and maps a picked point with decision 0001's formula (W01a: tests against a fake source, an update to two outputs interleaved included; manual check on niri; W01d: on Hyprland).
3. A lost Wayland connection or a protocol error makes the layout unknown and never ends the daemon; a source of another display is ignored (W01a, tests).

5. Each compositor's mapping of the absolute device across its screens is measured and recorded: niri on one output in 0004, on two outputs (one at a negative position) by W01a; Hyprland by W01c.
6. 7. Every request to Hyprland is bounded: one that never answers costs the recording its positions and nothing else; a position taken before a layout change is not written against the new layout (W01d, tests against a fake source).

## Open questions for the slices

Settled by W01a, 2026-11-12. The owner chose the source's shape (a crate of its own, joined to KWin by `Screens`), keeping the last whole layout during a change, matching KWin by process, trusting KWin when there is nothing to check against, and leaving two outputs for later; the rest are the slice's defaults, reviewed.
- **How the platforms hold the source.** Crate `backend-wayland` owns the connection (`Wayland`: `connect`, `none`, `layout`, `watch`, `missing`, `compositor`). (W01b removed `Screens`; see "Settled by W01b".) The daemon's `Screens` held KWin and the Wayland display: KWin's layout while it reports one, the display's otherwise. Its watcher runs both sources' watchers and passes on the fires of the source in use, since every fire refuses a pick begun before it: every fire of KWin's (in use, or just stopped being), and the display's while KWin has no layout. Each source fires only when its own layout changed, so a change undone before it was read still fires, and KWin taking over from the display with the same screens fires once (as KWin's first report did before W01). The sources are polled before the forwarding every time, and the forwarding runs outside the task's cooperative budget, so a change reaches the controller in the poll that read it. `Kernel` and `Portal` hold `Screens`; each source writes only its own layout. Tests (removed with it in W01b): `kwins_layout_wins_while_it_has_one`, `one_change_both_sources_see_fires_once`, `a_change_a_source_reports_on_its_first_poll_fires`, `a_change_undone_before_it_was_read_still_fires`, `a_change_a_source_reads_reaches_the_controller_in_the_same_poll`, `a_source_that_spends_the_budget_still_reaches_the_controller_in_its_poll`, `a_source_whose_watcher_ends_leaves_the_other_watched`.
- **A whole layout update.** Any output event (and a global added or removed) asks for a `wl_display.sync` round trip, one at a time; the layout is read once its answer and every event that arrived with it are handled, with nothing heard since the round trip was asked for and every output's update ended by its `done`, else the next round trip follows (an output's `done` asks for one). Each object's update ends at its own `done`: `wl_output.done` ends the output's, and with xdg-output 3 (which sends no `done` of its own) the xdg-output's too; with xdg-output 1 and 2, the xdg-output's `done` ends its own. A `wl_output` older than 2 sends no `done`, so nothing says when its update ends: it is not bound, and the layout is unknown while it is offered; niri's smithay, KWin and Hyprland offer version 4 (smithay `src/wayland/output/mod.rs:210`, KWin `src/wayland/output_interface.cpp:26`, Hyprland `src/managers/ProtocolManager.cpp:123`). `wl_output` is bound up to 4, the manager up to 3. Until then the last whole layout stands (W3). The collector decides whether the screens changed: an output came or went, or a place or size heard differs from the one before, even if a later update in the same round trip put it back (so a change undone before it was read still fires). A new scale, mode or a repeated notice with the same places and sizes is stored and fires nothing. No deadline: a compositor that never answers leaves the last layout, and nothing runs on a timer. Tests: `an_update_to_two_outputs_interleaved_is_never_read_half_done`, `a_round_trip_answered_before_an_outputs_done_reads_nothing`, `an_update_behind_the_answer_is_waited_for`, `with_xdg_output_2_each_object_ends_its_own_update`, `with_xdg_output_2_the_layout_waits_for_the_xdg_outputs_done`, `an_output_too_old_to_say_when_it_changed_leaves_the_layout_unknown`, `an_output_too_old_to_bind_leaves_the_layout_unknown_while_it_is_there`, `a_move_counts_even_when_undone_before_the_round_trip_came_back`, `a_move_undone_before_the_answer_still_fires`, `an_update_to_two_outputs_interleaved_publishes_once_whole`, `an_update_that_moves_nothing_fires_nothing`, `the_mode_turn_and_scale_reach_the_layout_and_fire_nothing`, `an_output_not_heard_in_full_leaves_the_layout_unknown`.
- **KWin belongs to the display, by process.** The daemon opens the display's socket itself (`WAYLAND_DISPLAY` under `XDG_RUNTIME_DIR`, or a path), never an inherited `WAYLAND_SOCKET`, and reads its listener (`SO_PEERCRED`) on that same socket. Each owner of `org.kde.KWin` counts when its process (`GetConnectionUnixProcessID`) is the listener or the listener's child: on Plasma 6.8 `kwin_wayland_wrapper` listens and `kwin_wayland` owns the name (0004). An owner reads as none until checked, so nothing is loaded into a KWin of another display and neither its layout nor its positions count, and a newer owner drops the check of the one before, the first owner's included. A lookup that fails, or a parent that cannot be read, is tried again after the watcher's back-off (2, 4, 8 s) and the KWin then counts; a process gone does not count. At exit, where the watcher may never have counted KWin, the owner is checked once and a lookup that fails unloads nothing: the next start cleans up. With nothing to check against (no display, a connection that failed, a listener outside the daemon's process namespace) KWin counts, as before W01. The listener is kept when the connection is lost, so a KWin restart under the same wrapper still counts. Tests: `kwin_counts_as_the_listener_or_its_child_only`, `the_kwin_of_the_display_is_swept_and_records_positions`, `a_kwin_of_another_display_is_ignored_and_called_for_nothing`, `each_new_owner_is_checked_before_anything_is_loaded`, `a_new_owner_reads_as_none_while_it_is_checked`, `a_new_owner_drops_the_check_of_the_one_before`, `a_new_owner_during_the_first_check_is_checked_at_once`, `a_lookup_that_fails_is_tried_again_and_then_trusted`, `a_kwin_whose_parent_cannot_be_read_is_tried_again`, `an_exit_that_cannot_tell_whose_kwin_it_is_unloads_nothing`, `without_a_display_to_check_against_kwin_counts_unasked`, `the_listener_of_a_socket_pair_is_this_process`; on Plasma, `plasma_kwins_owner_is_kwin_wayland_under_its_wrapper`.
- **The stored scale.** The current mode's width (its height when the output is turned a quarter) over the logical width, in thousandths, rounded; the whole scale without a mode, 1 without either. Stored, not compared. Test: `the_scale_is_the_mode_over_the_logical_size`.
- **The offset and what is not a layout.** Positions are `i32`; the box's corner is subtracted in `i64` and each result must fit `u32`, as must its far edge. An output without its place or size, of no size, past 16 outputs, or none at all leaves the layout unknown. The pick overlay subtracts the smallest left and top among winit's monitors from every corner, its own included; a monitor whose corner is not a whole logical px is left out, as before, and leaves its screen unmatched, so the pick is refused. Tests: `outputs_at_negative_positions_are_moved_to_start_at_the_corner`, `the_widest_spread_of_positions_still_fits_and_one_past_it_does_not`, `what_makes_no_layout_leaves_it_unknown`, `mirrored_outputs_on_one_rectangle_are_a_layout`, `corners_are_moved_by_the_smallest_left_and_top`, `the_overlays_corner_is_moved_as_the_monitors_are`, `monitors_at_negative_corners_match_the_layout_the_daemon_moved`, `a_point_on_a_layout_moved_from_negative_positions_maps_by_the_formula`.
- **Detection and its reasons.** At start, after the name is claimed and before KWin is served, within one 2 s deadline: connect, one round trip for the globals, bind, one more for the first layout. A display that answers too late keeps its listener, so KWin is still checked against it. A global withdrawn before the binds is never bound. The reasons kept for W01e (`Missing`, core's `NoScreens` since W01e): no display, cannot connect (or not in time), no xdg-output, connection lost, protocol error. A lost connection or a protocol error makes the layout unknown; the KWin half runs on. (W01a ended the watcher there for the daemon's life; since W01b a KWin restart on Plasma connects again, "Settled by W01b".) Tests: `the_display_is_found_under_the_runtime_directory_or_as_a_path`, `a_display_nobody_listens_on_cannot_be_connected`, `a_display_without_xdg_output_gives_no_layout_and_says_why`, `a_display_that_does_not_answer_in_time_keeps_its_listener`, `globals_withdrawn_before_they_were_bound_are_never_bound`, `two_outputs_give_one_whole_layout_at_start`, `an_output_plugged_in_later_joins_the_layout`, `a_lost_connection_makes_the_layout_unknown`, `a_connection_that_refuses_a_request_is_lost`, `a_protocol_error_makes_the_layout_unknown`, `an_event_the_client_cannot_read_is_a_protocol_error`, `a_handle_without_a_display_watches_nothing`, `a_second_watch_watches_nothing`; against the running compositor, `the_running_compositor_gives_a_layout_and_its_listener` and `the_running_compositor_reports_a_screen_change`.
- **libwayland in workspace builds.** The packaged daemon is built alone and stays pure Rust; a workspace build (tests, CI) links libwayland through the settings window's toolkit. libwayland reads an empty or closed socket as no events, so a read of no events looks at the socket itself (empty: wait again; closed: lost), and its protocol errors are read from the connection. One difference stays: an event the client cannot parse makes libwayland go quiet rather than fail. Test: `a_socket_is_closed_once_its_other_end_is_and_it_is_read_out`, and the client tests pass on both.
- **The spike injector** is left as it is; measurements use a Python uinput device, as 0004 did.
- **niri on two outputs** waits for a second monitor (the owner, 2026-11-12); one output at a negative position was measured (0004).
