# R03: Absolute cursor positions in recordings

- Issue: [#16](https://github.com/tobylo/auto-clicker/issues/16), a Feature under [G2 (#3)](https://github.com/tobylo/auto-clicker/issues/3), milestone M2. Slices: R03a (#51), R03b (#52).
- Maturity: refined 2026-11-10, ready to slice. Rests on [decision 0001](../../decisions/0001-cursor-position.md) (X01) and map D3, D4, D7, D11. Where this brief and decision 0001 differ (two scripts, the layout rule), this brief holds; the decision record marks those places.
- Diagram: [the flow from KWin to the file and back](https://prlens.dev/c/SSdbz2qLBRoW1UnAP_2jtw).

## Problem and outcome

A recording stores relative motion only. Replayed on the desktop it passes through pointer acceleration, so 400 units land 397 to 795 px away depending on speed (R02). With R03, a recording made on the desktop replays its clicks to the pixels they were made at, within 1 px per axis at scales up to about 1.8 (decision 0001). In a game that locks the pointer nothing changes: relative motion is recorded and replayed.

## Scope

In scope: reading the pointer position and the output layout from KWin while recording; storing both in the recording; replaying positions as absolute moves; falling back to relative motion; loading, unloading and cleaning up the KWin scripts.

Out of scope: sub-pixel positions (upstream wish 3 in decision 0001); rescaling positions to another layout; positions on compositors other than KWin; recording through the portal (P03); replacing the Ctrl+F7 hotkey (map, open questions).

## Invariants

These hold everywhere below and are stated once.

- **I1, a layout.** A layout is one or more outputs, each a rectangle of positive area in whole logical px with a scale, in a bounded number, whose bounding box starts at (0, 0) (KWin's own layouts always do, decision 0001). Anything else, from a file or from D-Bus, is not a layout: a file holding it is refused, and a report of it leaves the current layout unknown.
- **I2, a position.** A recorded position lies on at least one output of its recording's layout. The recorder drops a report that does not; a file holding one is refused.
- **I3, one validated form.** Reports from KWin are parsed once into the same types the file is parsed into. No sequence of reports makes a recording fail to finish, and the recorder never writes a file the program then refuses to load, by its content or its size.
- **I4, the current layout is known or unknown.** It is unknown until a script loaded by this daemon has reported the layout with the token of that load (the layout script, or the position script at its load while the layout script runs), and becomes unknown again the moment `org.kde.KWin` changes or loses its owner, a load fails, or a layout report is lost; nothing that load reported earlier makes it known again. (Since W01b the current layout comes from the Wayland display, and the position script's reports say which layout each position was taken on: [W01 brief](w01-other-desktops.md), W4 and "Settled by W01b".)
- **I5, every call to KWin is bounded** by its own deadline and ends at once on shutdown. A failure never blocks or fails a recording or the start of a playback: the recording carries on without positions, and a playback that starts while the layout is unknown uses relative motion. A playback already using positions is stopped instead ("Playback").

## Behaviour

**Recording.**
- While a recording runs, a KWin script reports `workspace.cursorPos` (whole logical px) once at load and on every change, a change within one pixel included: that report covers the relative move behind it, which the virtual mouse's own acceleration may carry across a pixel the real mouse did not (measured: one count of a high-resolution mouse that moved KWin's pointer less than a pixel replayed 2 px off before this). The daemon stamps each report on the event clock when it arrives.
- The recorder writes positions as events of their own, beside the relative moves it already writes. It keeps at most one position per millisecond, the latest; a press, a release or a turn of the wheel ends that millisecond, so the position before a click or a scroll is never replaced by one after it, unless the click, the scroll or the report is read more than 20 ms late ("Settled by R03a", late input). The first position after such an event is kept as it is, and counting starts with the next one: it may belong to the move before the event, and a later one must not stand in for it.
- The first position of a recording is written at the recording's start when no relative move came before it: the pointer has not moved since, so input in the few milliseconds the script takes to load still has its position.
- Events are ordered by time, not by arrival. A report is never stamped earlier than the move that caused it, so an input event read late goes before the positions stamped after it, where today it would be moved forward.
- A recording has one layout: the current one at its start. Positions are written only while the current layout is known and equal to it. So a recording started while the layout is unknown has no positions; a layout change ends them for good or until the layout is the recording's again; and after a KWin restart they resume only once the new layout script has reported the same layout.
- An idle recording still saves nothing: positions alone do not make a recording. The trip to the tray is trimmed as today; positions inside the trip go with its motion.

**Playback.**
- Positions are used when the current layout is known and every output a recorded position lies on is present in it with the same rectangle. A monitor added to the right of or below unchanged screens keeps positions exact; a screen that moved, changed size or is gone does not. Scale is not compared.
- Otherwise the whole run uses relative motion, as R02 does. When the recording holds positions that cannot be used, the tray tooltip says why while it plays; a recording without positions plays with nothing new shown.
- When positions are used, each is sent as an absolute move to `clamp(round(x * 65536 / W), 0, 65535)` (likewise y with H), W and H being the size of the current layout's bounding box (decision 0001's formula).
- A relative move is covered when a position follows it within 5 ms in the recording. A covered move is not sent. Every other relative move is sent (a locked pointer, KWin restarting, the pointer pushed against an edge).
- A press, a release or a turn of the wheel is never played between a covered move and the position covering it: that position is sent first, at that event's time, provided it follows the event within the delivery delay. A position that comes later than that belongs to motion after the event and stays where it is, and the move before the event is then sent as relative motion. A scroll acts on the window under the pointer, as a click does. A click on a pointer that has rested longer than the delivery delay (about 1 ms) therefore lands on its recorded pixel; a click made while the pointer still moves lands within what the pointer travels in that delay: which move a report belongs to cannot be known more closely.
- If the current layout changes or becomes unknown while a playback that uses positions runs, the controller stops it and says why. A relative-only playback carries on.

**KWin scripts.** W01b removed the layout script: the position script reports the layout at load and on every change, and the start still unloads a layout script an older version left ([W01 brief](w01-other-desktops.md), "Settled by W01b"). What follows is R03 as built.
- Two scripts, embedded in the binary, each under one fixed plugin name. The layout script stays loaded while the daemon runs and calls it once at load and on every layout change (the layout's size, the list of screens, or one screen's place or size), never on pointer motion. The position script is loaded only while a recording runs, and is unloaded however the recording ends; it reports the layout once at its load, taken while the layout script runs, so a change no call reported ends the recording's positions instead of going unseen.
- Every load first unloads its plugin name. At start the daemon unloads both names and sweeps its script files, so nothing a crashed daemon left stays; it does both only after it has claimed the single-instance name, and a process that fails to claim it touches neither. At exit it unloads both, however it ends once it holds the name, a failed start included.
- A layout load or a position unload that fails, the start's unload of a crashed daemon's position script included, is tried again while the daemon is idle: up to three more tries, 2 s, 4 s and 8 s after the failure before each, each wait with its own deadline. A new owner of `org.kde.KWin` and shutdown end the wait at once; a recording's start replaces a position unload waiting for its back-off with its own load, and a layout load keeps its deadline. When both wait, the earlier deadline serves both, so neither is put off by the other's failure. A call that succeeds or a new owner starts the count afresh, and a success also makes a call given up on due again; once the tries are spent the daemon logs it once and sets no timer, and the next recording loads a layout script given up on before its own. Every load unloads first, so an unload that fails is still tried before the next load and at exit. With nothing failed, nothing waits. A script directory that failed its check is never tried again (#59). (Since W01b, which removed the layout script, a position load that fails is tried again the same way while its recording runs: a KWin that just restarted does not answer for a moment. [W01 brief](w01-other-desktops.md), "Settled by W01b".)
- When `org.kde.KWin` gets a new owner the daemon loads the layout script again, and the position script if a recording runs.
- Without KWin on the bus nothing is loaded, nothing is started through D-Bus activation, and recording and playback work as in R02.

## Decisions

Decided by the owner (2026-11-10):
1. **Changed layout:** positions stay in use when the outputs the recording's positions lie on are unchanged; otherwise relative motion, with a tooltip. No refusing and no rescaling.
2. **The layout script stays loaded** for the daemon's lifetime. Decision 0001 describes one script, loaded only while recording, that reports positions and the layout size; that now describes the position script, and the layout comes from the second one.

Defaults (reviewed; go ahead without asking):
3. **D-Bus:** zbus 5, already a direct dependency. The receiver is an interface on the daemon's existing connection and name (`io.github.tobylo.AutoClicker`); no second name.
4. **Script files:** a private file (0600, created exclusively, no symlink followed, a unique file name per load) in a directory of the daemon's own under `$XDG_RUNTIME_DIR`. The scripts are loaded only when that directory is owned by the user and closed to everyone else, checked on the handle the file is created through.
5. **Trust:** a call is accepted only when its sender is the current owner of `org.kde.KWin` and it carries the token baked into the script at that load. This guards against stale scripts and stray callers. It is not a boundary against other processes of the same user, which can load KWin scripts of their own (decision 0001).
6. **Stored data:** logical positions, and per output its rectangle and scale, without names. Scale is stored, not compared: logical positions do not depend on it. Decision 0001's "playback must compare every output's rectangle and scale" is replaced by owner decision 1.
7. **Format:** version 2 is version 1 plus a `layout` field and an `"at"` event, under I1 and I2. A recording has either both a layout and at least one position (version 2) or neither (version 1, as written today, so older builds still read it). Versions 1 and 2 are read; a version 1 file with `layout` or `"at"` is refused. Version 2 is fixed when R03a merges: a later change takes a new version number.
8. **Skip rule:** the 5 ms window, with presses, releases and wheel turns kept after their position, as under "Playback". The file keeps raw moves and positions, so the rule can change without re-recording. The two errors are not alike: a desktop move wrongly sent is corrected by the next position, while a game move wrongly skipped (within 5 ms before an unlock) is a small lasting view error.
9. **Where it runs:** zbus handlers must be `Send` and run in order (no task per call), and the recording slot lives on the controller's thread. The handler stamps the call and passes it on; a watcher polled on the daemon's thread beside the controller feeds the recorder through the existing `RecordingFeed`, woken by its change counter and by calls, never by a timer. The controller remains the only one that starts or stops a recording.
10. **Layout check at play start** is one comparison against the current layout (I4): no new wait before playback.

## Acceptance criteria

R03a, each a test against the fake backend:
1. A version 1 recording plays exactly as before, with nothing new in the tooltip.
2. A recording with positions plays them as absolute moves at their times, does not send covered moves and sends the others.
3. A press, a release and a wheel turn between a move and the position covering it are each played after that position; a position before one of them survives a later one in the same millisecond.
4. A layout that moved or lost an output the recording used falls back to relative motion and says so; an added output beside unchanged ones does not; an unknown layout falls back.
5. The current layout changing or becoming unknown during a playback that uses positions stops it at once, with nothing pressed (time-bounded).
6. Format: version 2 round-trips; a recording without positions is written as version 1; the refusals of decision 7, I1 and I2 each have a fixture.
7. Recorder: events come out in time order when an input event is read late; one position per millisecond, with the first after a press, release or wheel turn kept; the first position written at the start when nothing moved before it; no positions while the layout is unknown or differs, and again once it matches; an idle recording saves nothing; the tray trim takes its positions.
8. I3: reports the recorder must drop never fail a recording, and the longest recording the recorder writes, with positions, loads.

R03b:
9. A call from anyone but KWin's owner, or with a stale token, is ignored (test).
10. Loading and cleanup with a fake KWin (test): scripts loaded and unloaded as "KWin scripts" says, on every way a recording ends; stale scripts and files removed at start, only after the name is claimed; a failed layout load and a failed unload tried again while idle, a bounded number of times, and nothing waiting with nothing failed (#59); scripts loaded again after a new owner; nothing loaded and nothing activated without KWin; a runtime directory open to others loads nothing.
11. The same on Plasma, by hand: nothing left after exit, and after a crash the next start cleans up.
12. Recorded clicks on desktop targets replay within 1 px per axis on one and two monitors (manual check on Plasma, numbers in the PR).
13. A recording that goes from the desktop into a pointer-locked game replays both parts (manual check on Plasma, with the measured delivery delay of a real mouse against the 5 ms window).
14. G2's "Record → play round trip" is ticked once criteria 12 and 13 pass.

## Open questions for the slices

Settled by R03a:
- **I3's size bound.** `MAX_FILE_BYTES` stays at 256 MiB. Each event counts the bytes it takes in the file at most, and the recorder stops itself when the next one would pass the budget (the cap less a 64 KiB reserve for the header, the layout and the releases at the end); the controller then saves it, as at the time limit, and the tray says it reached the largest size a recording may have. Tests: `a_full_recording_stops_and_its_file_stays_within_its_budget_and_loads`, `the_reserve_holds_the_largest_header_layout_and_release_at_the_end`, `a_recording_that_fills_up_stops_and_saves_at_once`.
- **The delivery delay** is `DELIVERY_DELAY_US`, 2 ms, beside the 5 ms `COVER_US` in `playback/plan.rs`; R03b checks it against a real mouse. Tests: `a_move_against_an_edge_then_a_press_then_a_move_away`, `a_position_later_than_the_delivery_delay_stays_and_the_move_is_sent`.
- **Late input among positions.** Input events keep the order they were read in, a late one moved forward to the last input event (reordering keys across devices could put a release before its press); positions go by their own time among everything, so a late input event goes before the positions stamped after it, and a motion bucket's move goes before a position stamped after the bucket's start. Positions and wheel turns wait until something stamped 20 ms later has been read (an input event, a report or a wheel turn), and only then is the one-per-millisecond rule applied in time order: a report is stamped when it arrives but fed to the recorder later (decision 9), so writing a click proves nothing about the reports before it. So a click read late, or a report fed late, still keeps the position before the click and the first after it, unless it is more than 20 ms late. A recording ends no earlier than its last position. Tests: `an_input_event_read_late_goes_before_the_positions_stamped_after_it`, `an_input_event_read_late_still_never_goes_before_an_input_event`, `a_motion_buckets_move_goes_before_a_position_stamped_after_its_start`, `a_click_read_late_inside_a_millisecond_keeps_the_position_before_it`, `positions_wait_for_late_input_twenty_milliseconds_at_most`, `a_report_delivered_after_a_click_it_came_before_keeps_the_first_after_the_click`, `wheel_turns_wait_twenty_milliseconds_at_most`, `reports_delivered_after_two_wheel_turns_keep_both_turns_apart`, `the_recording_ends_after_its_last_position`.
- **`Change::Position`**, a variant, so a recording stays one time-ordered list. The tray trim's walk back takes positions with moves (`the_tray_trip_takes_its_positions`); a chord modifier with only positions since stays droppable.
- **The stored rectangle.** `u32` logical px for x, y, width and height, as KWin reports them; at most 16 outputs, overlapping allowed; scale as `scale_milli`, an integer in thousandths. The file writes one object per screen: `{"x":0,"y":0,"width":2048,"height":1280,"scale_milli":1250}`. The formula runs in `u64` (`recording/layout.rs`). Whether a layout is the recording's, or still the one a playback started on, compares rectangles only (`Layout::same_screens`; `a_layout_differing_only_in_scale_keeps_positions`). Tests: `version_2_refuses_what_is_not_a_layout_or_a_position_on_it`, `positions_map_onto_the_whole_layout_by_the_formula`.
- **How the layout arrives.** `Platform::layout()` gives the current layout or `None` (the default), read when a recording starts and when a playback run begins. `Message::LayoutChanged`, without a value, makes the controller read it again. Each position reaches the recorder through `RecordingFeed` with the layout current when it was reported (`Recorder::position(time, point, current)`), so R03b's watcher passes the same layout `Platform::layout()` gives. Tests: `positions_are_kept_only_while_the_layout_is_the_recordings`, `a_layout_change_stops_a_playback_using_positions_at_once`.
- **P02** merged before R03a; R03a sits on it.
- **The plan** (covered moves, positions before a click) is worked out once when a recording is loaded, as event indices; a move at the same microsecond as a position before it is covered by that position, since at one time the order of a move and its report says nothing (`a_move_at_the_time_of_a_position_before_it_is_covered`); the layout is compared once when the run begins, and the tray's reason joins the notice a playback starts with.

Settled by R03b (the layout script's parts, and the tests that name it, went with W01b):
- **How the watcher is reached.** One `Platform` hook, `watch_layout(feed, changed)`, called once when the controller starts; the controller polls the watcher it returns in its one `select!`, after the hotkey events and before the running playback, and a fired `LayoutSignal` is handled as `Message::LayoutChanged` is (which stays), also before the playback: a change the watcher has received, or signalled, stops a playback using positions before its next event, so none plays on the old screens. The watcher is busy only while a recording moves the pointer, when nothing plays, and drains far faster than reports come; the hotkey reader stays last. The watcher holds no way into the inbox and starts and stops nothing. Tests: `the_layout_watchers_signal_stops_a_playback_using_positions_at_once`, `a_layout_change_is_handled_before_a_playback_event_due_with_it`, `a_layout_the_watcher_has_queued_is_taken_before_a_playback_event_due_with_it`, `the_layout_watcher_feeds_the_recording_the_controller_starts`.
- **The hand-off.** The receiver is a zbus interface with `spawn = false`, so calls are handled one at a time in arrival order (zbus spawns a task per call by default). A handler reads the clock, checks the sender and the token, parses, and `try_send`s into one bounded queue of 1024 reports for positions and layouts. The daemon runs on one thread, so a stalled thread delays the stamp as well; the queue fills only while the controller is busy outside its `select!`. A full queue drops the report: a gap in positions, and the recording carries on. A dropped layout report makes the layout unknown, ends that load's token at once and stops taking the position script's layout until its next load (what either queued before the loss is older than what was lost, and must not bring it back while the reload waits), and loads the layout script again. The watcher's call to KWin is a branch of its own, so reports never wait behind it. Tests: `calls_are_handled_one_at_a_time_in_the_order_sent` (fails with `spawn = true`), `a_full_queue_drops_reports_and_says_so_for_a_layout`, `reports_reach_the_recorder_in_order_and_at_once_while_kwin_hangs`, `a_full_queue_drops_positions_and_the_recording_carries_on`, `a_lost_layout_report_makes_the_layout_unknown_and_reloads_its_script`, `a_lost_layout_report_ends_the_old_load_while_a_call_is_in_flight`, `a_layout_the_position_script_sent_before_a_lost_one_is_not_taken`, `a_layout_call_on_the_bus_arrives_as_a_layout`.
- **Trust.** A call counts only from the current owner of `org.kde.KWin` (subscribed to `NameOwnerChanged` before it is read) with the token of a current load: 128 random bits, made current before the load is sent, since a script reports before `start()` answers. Tests: `only_kwins_owner_with_a_current_token_is_heard`, `a_layout_that_is_none_or_from_an_old_load_is_not_taken`, `without_a_layout_script_a_recordings_layout_is_not_kept`.
- **A stop and a start between two polls** are one wake: every change with a recording running loads the position script again with a new token, and the watcher handles a change before any report, so the old load's reports are dropped and the new recording gets its own first position. A position load still in flight when its recording stops or is replaced ends at once, and sends no more calls; the unload that follows, or the next load, which unloads first, takes away whatever it got to. Tests: `a_stop_and_a_start_between_two_polls_give_the_new_recording_its_own_position`, `a_stop_ends_a_position_load_still_in_flight`.
- **Values travel as text.** Each call carries the token and one string (`"x y"`, or `"x y width height scale"` per output, `;`-separated), parsed once into `Point` or `Layout`; how Qt marshals a script's numbers cannot break it. Tests: `a_position_is_two_whole_numbers`, `a_layout_is_every_output_with_its_scale`, `scales_round_to_thousandths`, `what_is_no_layout_is_refused`.
- **The clock.** `backend-kwin` takes a `fn() -> Duration`; the daemon passes `backend-kernel`'s `monotonic_now`, the input reader's clock, so there is no second `unsafe` copy.
- **A layout change no call reports.** No polling. The layout script also follows each screen's own geometry (two screens of one size swapped keep the layout's size and list), the position script reports the layout at each recording's start (taken only while a layout script runs: otherwise nothing would see it change afterwards), and the layout is unknown from the moment KWin's owner changes until the new layout script reports.
- **Loading and cleanup.** At start, files a crash left are swept; once KWin's owner is known, both plugin names are unloaded, then the layout script is loaded. Every load unloads its name first, and a failed unload ends that load; at exit, however the daemon ends once it holds its name (a device that fails to open included), both names are unloaded from KWin's owner, asked for when the watcher never saw it, and their files removed, within two calls' 2 s deadlines. Without KWin nothing is called. The script directory is opened without following a symlink and checked on its handle (this user's, mode closed to others); files are created through that handle, exclusively, 0600, named after the load's token. Each call to KWin goes to its unique name with `NO_AUTO_START` and a 2 s deadline. A loaded script is started with `/Scripting`'s `start`, which starts every loaded script not yet running, never with `run` on the id `loadScript` returns: KWin numbers a script by how many are loaded (`src/scripting/scripting.cpp:815` in 6.8.2), so after another script is unloaded the id can be one a running script holds, and `/Scripting/Script<id>` then reaches that one while the new script never runs (seen on the laptop, where it left the layout unknown). Tests: `the_start_sweeps_then_loads_the_layout_script`, `without_kwin_nothing_is_loaded_and_nothing_is_called`, `a_recording_loads_the_position_script_and_its_end_unloads_it`, `a_failed_unload_is_tried_again_before_the_next_load_and_at_exit`, and for the retry while idle (#59) `a_layout_load_that_fails_once_is_tried_again_after_its_back_off`, `a_position_unload_that_fails_once_is_tried_again_after_its_back_off`, `a_kwin_that_keeps_failing_is_left_alone_until_its_owner_changes`, `a_recording_or_a_new_owner_during_a_back_off_acts_at_once`, `a_recording_during_a_layout_back_off_loads_first_and_the_layout_follows`, `with_nothing_failed_the_watcher_sets_no_timer`, `a_script_directory_that_failed_its_check_is_not_tried_again`, `an_unload_that_fails_after_the_next_recording_started_leaves_its_load_due`, `a_layout_load_given_up_is_tried_again_at_the_next_recording`, `a_crashed_daemons_position_script_that_fails_to_unload_at_start_is_tried_again`, `a_second_failure_does_not_put_off_a_call_already_waiting`, `a_position_script_loaded_during_a_layout_back_off_reports_no_layout`, `a_recording_during_the_starts_layout_load_keeps_a_failed_sweep_unload`, `an_unload_whose_tries_the_layout_spent_is_tried_again_once_kwin_answers`, `a_report_lost_during_the_last_try_does_not_add_another`; `an_exit_before_the_watcher_ran_unloads_what_a_crash_left`, `a_new_owner_of_kwin_gets_the_scripts_again`, `a_runtime_directory_open_to_others_loads_nothing`, `a_new_owner_does_not_wait_for_a_call_to_the_old_one`, `a_call_that_never_answers_ends_at_its_deadline`, the `dir` tests; on Plasma, `plasma_scripts_load_report_and_unload`, `plasma_a_crashed_daemons_scripts_are_unloaded_at_the_next_start` and `plasma_a_script_given_the_id_of_a_running_one_still_runs` (fails with `run` on the id).
- **Only after the name is claimed.** `Kwin::serve` takes the connection that holds the claimed name (`instance::Claim::connection`), and a process that fails to claim it returns before. Nothing is loaded until the controller runs; the exit's unloads run however the daemon ends once it holds the name, a failed start included, and are the only calls to KWin without a controller.
- **The user service after a crash.** The unit restarts the daemon on failure (`Restart=on-failure`, 5 s, backing off to 5 min), and the start's sweep unloads a stale position script then. A daemon started by hand is cleaned up at its next start. The unit stays as it is.
- **The portal route.** Criterion 12 is measured on both output routes; if the portal route misses, it plays relative motion and a follow-up issue takes it.

Settled by the manual checks on the laptop (KWin 6.8.2, 2026-11-11, a Razer Viper V3 Pro):
- **Clicks land on their pixels.** Every replayed click landed on its recorded pixel, or within 1 px per axis: on two outputs (2048×1280 at 1.25 beside 3440×1440 at 1) and on one, corners and edges included, on the kernel route (29 clicks over five recordings, 28 exact; the one miss, 2 px, came before the fix below) and on the portal route (6 clicks, 5 exact, one at (0, 0) replayed at (1, 1)).
- **A move within one pixel is reported.** The script first skipped a report that left the whole-pixel position as it was; the move behind it then played through the virtual mouse's own acceleration and moved a click 2 px. Every change is reported now.
- **The delivery delay.** Over 9,756 moves, the position followed its move by 0.81 ms (median), 1.91 ms (99th percentile) and 2.19 ms (99.9th); 28 took longer than 2 ms and one longer than 5 ms.
- **A game holding the pointer.** KWin's pointer does not move while a game holds it, so no position is recorded then, nothing absolute is sent, and the moves play as relative motion: a recording from the desktop into Minecraft and back replayed its desktop clicks on their pixels and ended on the recorded view (19.6 / 47.4). The pointer the game centres when it takes hold is recorded as a position and plays without effect on the view. No move inside the hold had a position within 5 ms after it, so the 5 ms window skipped none.
- **KWin's load.** While a recording runs and the mouse moves (about 1,800 reports a second from the mouse, 535 positions a second from the script), KWin used about 68 % of a core against 47 % for the same motion without recording; idle, 5 %.
- **A script's file** stays until its script is unloaded: `start` answers before KWin has read the file, so nothing tells when it could go sooner.
