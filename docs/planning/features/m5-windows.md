# M5: Run on Windows 11

- Milestone M5, scope gate G5 (#107). Investigation X03 (#109), slices WN01 (#108), WN02 to WN12 (#110 to #120), WN06b (#132) and WN06c (#135); [github-map.json](../github-map.json) maps the codes.
- On Windows this brief replaces map D1's tray, D7's paths, file calls and input reader, and D12's layer-shell surfaces; everything else in the map holds on both systems.
- Maturity: mapped and settled 2026-11-23, before the spike. X03 measured the mechanisms on 2026-11-25 ([decision record 0006](../../decisions/0006-windows.md)); decisions 5, 6 and 9 and invariant N5 changed with the owner that day, and decisions 2, 7 to 10 and 15 gained what the spike measured.
- Diagram: [what stays, what Windows adds, and a hotkey click with a kill mid-hold](https://prlens.dev/c/IqawE6ShSVjC6_CUfjrqQg).

## Problem and outcome

The program runs only on Linux. Games run on Windows too, and the owner wants the same tool there. With M5 a user on Windows 11 gets the same program: a tray icon, Ctrl+Shift+F6 to click in the game, recording and playing routines, the settings window, and the countdown and badges on the screen.

## Scope

In scope: Windows 11 on x64, with feature parity with Linux v1 and O01: clicking, hotkeys, recording and playback with positions, the tray, the settings window, the on-screen display, English and Swedish. A test VM on the dev box. Install by building a reviewed commit on the Windows machine.

Out of scope: Windows 10; ARM64; macOS; games whose anti-cheat ignores injected input (the guide names the limitation, and the program never installs a driver or uses one, such as Interception); running elevated, and so games running elevated: an elevated daemon would read config, recordings and its own binary from places any unelevated program of the user can write, and become a way past UIPI, so the daemon refuses to start elevated and says why; an installer, code signing and an updater.

## Decisions

1. **One controller, both systems.** Core (controller, engine, recorder, config, recordings, the window's protocol, messages) is shared. Windows adds a backend, not a second design.
2. **Keys stay Linux key codes** in core, config and recordings. The Windows backend maps them to and from scan codes, and injects by scan code with the extended flag where a key needs it, since games reading raw input or DirectInput read scan codes. X03 measured injected scan codes arriving as the real keyboard's do, E0 keys with the extended flag; NumLock goes without it, and Pause, an E1 sequence, only by virtual key (0006 point 1).
3. **One crate, `backend-windows`, holds every Win32 call:** output, the watchdog's shared table, the message thread, hotkeys, raw input, screens and positions, the tray, single instance, session state and the on-screen display. Bindings come from `windows-sys`. `unsafe` stays in that backend, as the hard rule says. The Linux crates build only on Linux, through target-specific dependencies rather than scattered `cfg`. Core's own Unix file code (`fs.rs`, config reads, the recordings library) is ported, not hidden: core builds and tests on both systems. Windows-only dependencies are checked by the same advisory and licence gate as the rest.
4. **One Win32 message thread** owns every window, the tray icon, hotkeys, raw input and session notices. It sleeps in `GetMessage` while idle, sends the controller messages and changes no state itself. The controller and engine stay on tokio's single-thread runtime. Map D11 is amended to allow this second thread on Windows. At shutdown the thread is told to quit and joined with a deadline. Amended by WN07 (2026-11-26): the tray icon's shell calls (`Shell_NotifyIconW`) run on a thread of their own, since they wait on Explorer without a limit (58 s and counting in the VM with Explorer suspended) and the message thread must hear a lock or a sleep at once; that thread sleeps on a condition variable while idle, and the message thread keeps the window, the menu, the popup and every notice. Amended by WN06 (2026-11-26): the daemon's wait on its watchdog's process is a thread of its own, asleep on the process and a stop event, which sends the controller Quit when the watchdog ends, directly, so neither a full message queue nor an open tray menu holds it up.
5. **Timing.** On Windows a run's deadlines are waited for by a high-resolution waitable timer (`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`) on a thread that exists only while a run is active: it sleeps until each absolute deadline and wakes the runtime, and a stop or shutdown ends its wait at once. The engine gets its deadline wait through the backend interface, so core stays free of Win32: tokio's `sleep_until` on Linux and in the fake backend, where engine tests keep tokio's paused clock, and the waitable-timer thread on Windows, with stop tests of its own. While a run is active, and only then, the daemon also opts out of power throttling for execution speed, and asks Windows to keep the display on (`SetThreadExecutionState` with `ES_DISPLAY_REQUIRED`), since the display turning off stops a run (decision 15) and a hold sends no input to keep it on (owner, 2026-11-25). Nothing raises the system's timer resolution (`timeBeginPeriod`). The 10 ms floor stays on both systems. X03 measured tokio's own sleep, even with 1 ms resolution and the opt-out, waking 0 to 2 ms late, so a fifth of 10 ms periods missed by 10 % or more; the waitable timer waking tokio held 10 ms with a 99th-percentile error of 0.41 ms (0006 point 2; changed with the owner 2026-11-25, VM-only until real hardware).
6. **Nothing stays pressed after the process dies.** Windows does not release what a dead program held. A watchdog, a small program of its own (`auto-clicker-watchdog.exe`, so a kill by the daemon's name does not take it), is what starts at login: it starts the daemon as its child, shares a fixed-size table of held keys and buttons with it, waits on the daemon's process, and releases whatever the table holds when the daemon ends. Being the parent, it survives "End process tree" on the daemon. The daemon sends no press before the watchdog is attached, records a press in the table before sending it and clears it only after the release is delivered (decision 7's check), so no click waits on I/O. The table has one byte for every Linux key code up to `KEY_MAX`, buttons included at their own codes, so it is never full (WN06, 2026-11-26). The watchdog reads the table as untrusted: bounded, validated, releases only. Its release follows decision 7: a release it cannot count as delivered stays in its table and is sent again, and the watchdog exits only once every entry is delivered, since killing the daemon from Task Manager leaves elevated Task Manager in front and drops the first release without an error (0006 point 7; changed with the owner 2026-11-25). That wait has no deadline: like the daemon's idle wait, the watchdog sleeps on the foreground and desktop events and costs nothing, and it ends at delivery or when the session ends. Unwinding guards still cover panics, as on Linux. What remains: killing the watchdog and the daemon together (the watchdog's own tree) and logging off; the guide names both.
7. **A release Windows blocks is sent again.** UIPI drops injected input while an elevated window has focus, and SendInput still reports success; on the secure desktop (lock, UAC) SendInput fails with access denied. A held key whose release may not have arrived stays in the table and is released again once the user's desktop has input again. Neither the return value alone nor the key state decides it: after a lock the system reports the key up while the game never saw it come up, and an unelevated program reads every key up while an elevated window is in front. A release counts as delivered only when, both before and after SendInput, the user's desktop has input (`OpenInputDesktop` succeeds) and the window in front belongs to a process whose integrity is readable and not above the program's own, with no foreground or desktop change in between; anything else keeps it for sending again. The signals to try again are a foreground change (`EVENT_SYSTEM_FOREGROUND`) and the input desktop coming back (`EVENT_SYSTEM_DESKTOPSWITCH`; for the lock also `WTS_SESSION_UNLOCK`; a UAC prompt raises no session notice). Measured in X03 (0006 point 6).
8. **Own events.** Every injected event carries the program's marker in its extra information. The recorder and any input reader drop marked events. Another program's injected input counts as the user's, as another uinput device does on Linux. Raw input gives every injected event device handle 0 and keeps only the low 32 bits of the extra information, so the marker is a non-zero 32-bit value and is the only thing that tells the program's events from another injector's (0006 point 3).
9. **Hotkeys** through `RegisterHotKey` with `MOD_NOREPEAT`, defaults unchanged (map D6), rebound in the settings window, which captures the keys from its own window events while the daemon's hotkeys are unregistered. A hotkey message carries no marker, so, as on the portal route (P02), the program never presses a hotkey's key: a run that would is refused, judged by the registered bindings. A hotkey message says nothing about the keys coming up, and the controller starts a run only once the hotkey's modifiers are up (so the game never gets Ctrl+Shift+click): from a hotkey's activation until its modifiers are up, or the existing 30 s cancel, the backend registers raw keyboard input and reads only whether the modifiers are down, logging nothing. A combination another program holds is refused by Windows: the tray names the hotkey and the reason, as map D2 does for a missing route, and a save registers the new set before releasing the old one, so a refused combination refuses the whole save. X03 measured the hotkey firing with game-like windows in front and from SendInput, once per press; the game gets the modifiers but not the hotkey key's press; the modifier wait registered within 0.24 ms and missed no release. A window in front that registers its keyboard with `RIDEV_NOHOTKEYS` turns every registered hotkey off while it has focus (0006 point 5), so while a run is active the backend also registers raw keyboard input and matches only the combinations of the hotkeys that stop the running job, the same set as on Linux (any of the three during playback), from unmarked events, logging nothing: a run stops by its hotkey whatever the game in front does (changed with the owner 2026-11-25). A press that arrives both as `WM_HOTKEY` and through raw input counts as one activation, in either order, so a stop never turns into a restart. The guide names such games, since starting a job by hotkey does not work while one has focus.
10. **Recording** reads raw input (keys, buttons, relative motion), registered only while a recording runs (and, for the modifiers alone, decision 9's wait; during a run, for the hotkeys that stop it). Positions come from the pointer's position on each mouse move, and the layout from the monitors, in physical pixels with per-monitor DPI awareness. Low-level hooks are used only if X03 shows raw input cannot see what recording needs, because Windows silently removes a hook that answers slowly. X03 measured raw input with `RIDEV_INPUTSINK` seeing keys, buttons and motion behind every kind of window in front, so no hooks (0006 point 4).
11. **Recordings name where their positions came from.** A recording made on Windows says so. Playback uses positions only from the system and layout they were made on, and relative motion otherwise, with the notice Linux gives for a changed layout.
12. **Files.** The same formats, under `%APPDATA%\auto-clicker` (config) and `%LOCALAPPDATA%\auto-clicker` (recordings, state, logs). Atomic writes keep Linux's guarantees, the checked directory being the one written to included: replace by rename, create-new by a hard link then removing the temporary file, no-follow through the reparse-point flag. Linux reaches every name through the checked directory's open handle; std has no such call on Windows, so there the directory's path is resolved once into one through no junction, the directory itself is refused if it is a reparse point, and it is held open without delete sharing, so nobody can rename or delete it while it is held, and that resolved path keeps naming it (WN02, settled 2026-11-24). A held folder also stops its parent and grandparent being renamed, as a Windows test shows, so only the folder itself is held. Core stays free of `unsafe` and uses std alone, as cap-std's own Windows code does the same. Each file is flushed (`sync_all`) before the rename or link. Windows has no directory fsync, so that step of AGENTS.md's rule does not apply there. A sharing violation from an antivirus scanner or the indexer is transient, not "missing".
13. **Language** from the user's display language. Logs go to a file, since a program without a console has no output.
14. **The settings window** is the same Slint program on Slint's Windows backend. It talks to the daemon over its standard input and output pipes instead of a socket pair. The renderer is femtovg if it works on Windows, otherwise Slint's software renderer (WN10 decides).
15. **The tray** re-adds its icon when Explorer restarts (`TaskbarCreated`). Locking, switching user, sleep and the display turning off stop a run, as logind's facts do on Linux (the display since Modern Standby may announce no sleep; WN05). The on-screen display's windows (topmost, layered, click-through, non-activating) took no focus and no input from the window under them in X03; a topmost window activated later covers them until they re-assert topmost (0006 point 8).
16. **Install:** the owner builds a reviewed commit on the Windows machine (`cargo build --locked --release`, MSVC toolchain). A PowerShell script, run with `-ExecutionPolicy Bypass`, copies the programs to `%LOCALAPPDATA%\Programs\auto-clicker`, registers the watchdog (which starts the daemon) to start at login under the user's `Run` key, upgrades a running install by asking the daemon to quit first, and uninstalls. The program is unsigned: SmartScreen asks before the first run, and Defender may flag a program that injects input; the guide says how to allow it.
17. **Tests.** A `windows-2025` CI job runs the gates of `scripts/gates.sh` on the workspace, and cargo-deny checks the Windows target too. Before a commit, Windows-only code is checked on the dev box with clippy for the Windows target, and its tests run in the VM. Device tests on Windows are `#[ignore]`d and run in the test VM (WN01) by the session, through a scheduled task in the VM's logged-in desktop, since a program started over SSH has no desktop to inject into (WN01). The PR names the VM's Windows build. What needs a real graphics card (a game at full speed, fullscreen behaviour, timing without a hypervisor) is measured on real hardware when the owner has some, and marked as VM-only until then.

## Invariants

- **N1, no second writer.** Everything Windows adds sends the controller messages; none of it changes state.
- **N2, idle costs nothing.** Idle on Windows is the message thread asleep in `GetMessage`, the runtime asleep, the daemon's wait thread asleep on the watchdog's process, the watchdog asleep on the daemon's handle. No run timer thread exists, no timer resolution is raised, no raw input is registered and nothing polls.
- **N3, every exit releases.** Stop, error, panic, lost output, session lock, sleep, shutdown and the daemon's death, its process tree included, each release every key and button the program holds; a release Windows blocked is sent again (decision 7). The only exceptions are the last sentence of decision 6. Every stop test has a time bound well under the wait it interrupts.
- **N4, never reacts to itself.** No marked event is recorded or counted as user input, and the program never presses a hotkey's key. The marker is a filter, not an identity check: another program could copy it.
- **N5, the keyboard is read only while needed.** Raw keyboard input is registered only while a recording runs; while a run is active, when only the combinations of the hotkeys that stop it are matched; and while a hotkey's modifiers are still down after its activation (decision 9), when only the modifiers' state is read. Nothing outside a recording is logged or kept.

## X03: the spike, in the VM

X03 runs in the WN01 VM and ends with decision record 0006. It measures:

- SendInput clicks and keys reaching a test window and Minecraft Java (if it runs on the VM's OpenGL), counted as C02 counted them, at the 10 ms floor;
- interval accuracy at 10, 12 and 15 ms under tokio, with and without decision 5's settings, with all of the daemon's windows hidden (in a VM, so marked as an upper bound);
- what the marker and the raw-input device handle show for injected events, and whether a program can tell its own events from another injector's;
- whether raw input with `RIDEV_INPUTSINK` sees keys, buttons and relative motion while another window, including one reading raw input itself, has focus;
- whether `RegisterHotKey` fires while a game window has focus, whether the game also gets the keys, and whether a combination sent with SendInput fires it; how soon after an activation raw input reports the modifiers coming up;
- whether a release is delivered while an elevated window has focus and after a lock, and when it can be sent again;
- that a key pressed with SendInput stays down after the process is killed, and that a watchdog's release clears it, including after "End process tree" on the daemon;
- a topmost, click-through, non-activating window over a borderless window, taking no focus and no input.

Results: [decision record 0006](../../decisions/0006-windows.md), measured 2026-11-25 on build 26300.9974.
